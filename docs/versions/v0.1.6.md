## Added

- **O11 GDI+ fallback engine for the image strip pipeline.** On O11 hosts where the Magick.NET native library refuses to initialise (typical on locked-down environments such as the OutSystems Personal Environment sandbox on `outsystemscloud.com` — `System.TypeInitializationException` on `ImageMagick.NativeMagickSettings`, HRESULT `0x8007045A` / `ERROR_DLL_INIT_FAILED`), the extension catches the exception on first use, latches an AppDomain-scoped `_magickBroken` flag via `Interlocked.Exchange`, and routes every subsequent image strip through a pure-managed `System.Drawing` (GDI+) engine. GDI+ (`gdiplus.dll`) is a Windows built-in KnownDLL always loaded from `System32` and is not subject to the loader / EDR / WDAC policies that block the native ImageMagick runtime. The dispatch is transparent to the caller: `MssStripFileMetadata` continues to accept the same inputs and return `RecFileMetadataResult` with the same four fields (`CleanFile`, `ExtractedMetadata`, `RemovedEntryCount`, `IsPassthrough`) — no interface change, no new field, no XIF-metadata edit required. Ships as a new `FileMetadataStrippingActions.Images.Gdi.cs` partial (in both the O11 project and the XIF source folder) and adds a `<Reference Include="System.Drawing" />` to the O11 csproj (framework GAC assembly, no NuGet package, no new supply-chain surface). ODC (`net10.0`) is unaffected — the sandbox constraint is O11-specific and `System.Drawing.Common` on .NET 6+ is Windows-only.

- **O11 native-DLL preload guard.** `MssStripFileMetadata` now calls a best-effort `EnsureMagickNativePreloaded` on entry that resolves `Magick.Native-Q8-x64.dll` from an absolute path next to the extension assembly and loads it via `LoadLibraryExW` with the `LOAD_WITH_ALTERED_SEARCH_PATH` flag (`0x00000008`), which forces Windows to use the DLL's own directory as the search root for its dependent DLLs — resolving the bundled VC++ 2015-2022 x64 runtime and BCL shim DLLs staged in `bin/` instead of relying on `System32`. A belt-and-braces `SetDllDirectoryW(binDir)` call adds the extension's bin folder to the process-wide DLL search path. The guard is idempotent (`_preloadState` gated with `Volatile.Read` / `Interlocked.Exchange`), thread-safe, silently no-ops on healthy hosts where the default search order already works, and is completely absent from the ODC path. Maximises the set of hosts on which the primary Magick.NET engine initialises successfully; on hosts where the preload itself is refused it is a silent no-op and the GDI+ fallback takes over on the first image call.

- **`FileMetadataStripping.O11.GDI.Tests` mirror test project (net48).** New 545-test xUnit assembly that exercises the same per-format, per-category, per-passthrough-case matrix as the primary O11 suite but with every image test forced through the GDI+ fallback path. The mirror project's local `FileMetadataStripping` adapter type has a static constructor that calls `CssFileMetadataStripping.ForceGdiFallbackForTesting()` — a single `internal` seam exposed to the mirror project via `[assembly: InternalsVisibleTo("FileMetadataStripping.O11.GDI.Tests")]`, gated to that one assembly, with no effect on production callers or on the primary `FileMetadataStripping.O11.Tests` project. The mirror asserts the three-way result contract described below, guarantees the fallback engine keeps pace with the primary engine on every change, and closes a Stage 3 (functional-regression-detector) regression window that the primary tests alone could not catch. Assembly-level `DisableTestParallelization` keeps the shared `_magickBroken` static latch stable. Documents, SVG, media and passthrough tests are shared verbatim with the primary O11 project via `<Compile Include="..\FileMetadataStripping.O11.Tests\… Link=…" />` — a single source of truth for pipelines that never touch Magick.NET.

- **HEIC brand-coverage regression lock.** `DetectImageFormatByMagicBytes` now recognises every ISOBMFF `ftyp` major brand that `IsHeifOrAvifBrand` recognises — including `hevc`, `hevx`, `heim`, `heis` (the most common iPhone HEIC brands) alongside the primary `heic` and `heix`. Six new theory tests in `GdiUnsupportedFormatTests` (`IPhoneHeicBrands` member data) assert that a `hevc`-branded HEIC on a broken-Magick host still routes to the GDI+ unsupported-format error contract, not to a silent `IsPassthrough=true`. Prevents a security-signal downgrade found by the functional-regression-detector during Stage 3 of this cycle.

## Changed

- **O11 image strip result contract now has three deterministic shapes when the GDI+ fallback engine is active.** Behaviour on healthy hosts (Magick.NET path) is byte-identical to v0.1.5.

  1. **Actively stripped** — JPEG, PNG, GIF (single-frame; multi-frame animation timing is best-effort under GDI+), BMP, TIFF (single-page; multi-page handled via `SaveAdd(FrameDimensionPage)`) → `IsPassthrough = false`, `RemovedEntryCount > 0` when the input carried EXIF / IPTC / GPS / thumbnail / XMP / property items, `ExtractedMetadata` is a JSON object `{"gdiPropertyItems": ["Make", "Model", "GpsLatitude", ...]}` listing the friendly names of every `PropertyId` removed via `System.Drawing.Image.RemovePropertyItem`. Unknown property IDs are exposed as `PropertyId_0xNNNN` so the audit remains actionable.

  2. **Recognised-but-unsupported** — WebP, HEIC, HEIF, AVIF, JXL, JP2, J2c, JXR, PSD/PSB, DDS, EXR, HDR, DPX, CIN, FITS, QOI, SGI, SUN, PCX, DCX, PNM, JBIG, XCF, WMF, ICO, DCM, TGA, MNG, and every camera RAW variant (ARW / CR2 / DNG / NEF / ORF / PEF / RAF / X3F) → `IsPassthrough = false`, `RemovedEntryCount = 0`, `CleanFile = originalBytes`, `ExtractedMetadata` contains a JSON `processingError` value prefixed with the fixed marker `"GDI+ fallback:"` followed by the format name and a short explanation. This is an **explicit failure signal** — deliberately NOT a silent passthrough. Setting `IsPassthrough = true` here would be a security-signal downgrade: the file DOES carry metadata containers and the fallback engine did NOT strip them, so consumers must be able to react (log-and-reject, retry through an alternate pipeline, quarantine).

  3. **Unrecognised bytes** — plain text, PDF (routed to the PDFsharp path before the image dispatcher runs), arbitrary bytes → normal `IsPassthrough = true` passthrough. Unchanged from v0.1.5.

  Consumer-facing predicates on the O11 side:

  | Outcome | Predicate |
  |---------|-----------|
  | *Actively stripped* | `IsPassthrough == false && RemovedEntryCount > 0` |
  | *Fallback declined to strip* | `IsPassthrough == false && RemovedEntryCount == 0 && ExtractedMetadata.Contains("GDI+ fallback:")` |
  | *Not an image / not in scope* | `IsPassthrough == true` |

  The Documents / SVG / Media / Passthrough pipelines never touch Magick.NET and are completely unaffected by the fallback — identical behaviour on both engines.

- **`FileCategory.Image` dispatch now goes through `StripImageMetadataWithFallback`.** The private `StripImageMetadata` from v0.1.5 was renamed to `StripImageMetadataWithMagick` (unchanged body) and is now called from a new dispatcher that checks the `_magickBroken` latch, catches `TypeInitializationException` on the first Magick.NET call, latches the flag, and forwards to `StripImageMetadataWithGdi`. `DetectCategory` was extended in parallel: it now catches `TypeInitializationException` from `MagickImageInfo` (previously only `MagickException`) and, when the latch is set, falls through to a pure-managed `DetectImageFormatByMagicBytes` so JPEG / PNG / GIF / TIFF / WebP / HEIC / HEIF / AVIF / JXL / JP2 / JXR / PSD / DDS / EXR / HDR / SGI / DPX / Cin / Sun / DCX / PCX / Pnm / Xbm / Xpm / JBIG / Xcf / Wmf / ICO / DCM / TGA are still routed to the image path (and receive the correct three-way contract) instead of silently returning `Passthrough` on the sandbox.

## Fixed

- **O11: `System.TypeInitializationException` on `NativeMagickSettings` when calling `StripFileMetadata` on the OutSystems Personal Environment sandbox.** The failure surfaced identically to the OSStegoGuard v0.1.2 field report: `System.TypeInitializationException: The type initializer for 'NativeMagickSettings' threw an exception ---> Unable to load DLL 'Magick.Native-Q8-x64.dll': A dynamic link library (DLL) initialization routine failed. (HRESULT: 0x8007045A)`. Root causes on the sandbox are host-side (native-code loader policy on `outsystemscloud.com` refuses to complete `DllMain` on `Magick.Native-Q8-x64.dll` regardless of DLL search-path adjustments or bundled runtimes), not something the extension can fix from user mode. This release layers the same three mitigations OSStegoGuard v0.1.2 shipped — `EnsureMagickNativePreloaded` guard on every entry, bundled BCL shims + VC++ 2015-2022 x64 runtime already staged in the XIF `bin/` (pre-existing since earlier cycles), and the new `System.Drawing` (GDI+) fallback engine that engages the first time `TypeInitializationException` is thrown and stays engaged for the rest of the AppDomain. On hosts where Magick.NET works — every current test host and every production O11 install other than the OPE sandbox — the latch stays `false`, the preload succeeds silently, and behaviour is byte-identical to v0.1.5.

- **HEIC `hevc` / `hevx` / `heim` / `heis` major brands no longer route to silent passthrough on broken-Magick hosts.** The first attempt at the pure-managed image detector recognised only `heic` and `heix` HEIC brands. A `hevc`-branded HEIC (the most common brand on iPhone Camera Roll exports) would slip through the early `DetectImageFormatByMagicBytes` check, get routed to `FileCategory.Image` via the `IsHeifOrAvifBrand` fallback in the ISOBMFF `ftyp` scan, then land in `StripImageMetadataWithGdi` where the same narrow brand list returned `null` — producing `IsPassthrough = true` for a file that DOES carry EXIF / GPS / thumbnail metadata. Widened the pure-managed detector to match `IsHeifOrAvifBrand` exactly (any `he*` prefix + `mif1` / `msf1` + `avif` / `avis`) and locked the invariant with six new theory tests (`IPhoneHeicBrands`) in `GdiUnsupportedFormatTests`. Only affects hosts where the GDI+ fallback engages; the healthy Magick.NET path already handled all these brands correctly.

## Development note — intentional O11/ODC test parity break

The Change Cycle's Stage 3 (`functional-regression-detector`) enforces byte-for-byte parity between the ODC and O11 test suites via the shared `TestHelpers` adapter pattern. This cycle introduces one deliberate, documented exception (mirroring the OSStegoGuard v0.1.2 exception):

- **`FileMetadataStripping.O11.GDI.Tests/`** (the entire mirror test project) has **no counterpart** in `FileMetadataStripping.Tests/` (ODC).

Rationale: the GDI+ fallback engine itself is O11-only (`net48`, `System.Drawing`) and its deterministic tests depend on the `internal` seam `ForceGdiFallbackForTesting()` exposed exclusively to the mirror project via `[InternalsVisibleTo("FileMetadataStripping.O11.GDI.Tests")]`. There is nothing meaningful for the ODC test project to mirror — the ODC path has no fallback engine, no `_magickBroken` latch, and no `System.Drawing` dependency. Future contributors should **not** create an ODC-side mirror of `FileMetadataStripping.O11.GDI.Tests/` to satisfy the parity checker; the divergence is intentional and load-bearing.
